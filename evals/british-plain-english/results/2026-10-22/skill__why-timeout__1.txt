Retrying is safe only if the endpoint is idempotent in the strict sense, which means that sending the same request several times has the same effect as sending it once. A plain POST that creates an order is normally not idempotent, so I would confirm the claim before relying on it.

The risk comes from the timeout. The server may have created the order and the reply may have been lost on the way back, so your script cannot tell whether the first attempt worked. If the endpoint treats each POST as new, the retry creates a duplicate order.

The usual fix is an idempotency key, which is a unique ID you send with the request, often in an `Idempotency-Key` header. The server remembers the key and returns the original result for a repeat instead of creating a second order. Check that the `/v2/orders` documentation describes this. Then make sure your script generates the key once per order and sends the same key on every retry. A new key per attempt defeats the protection.

It also helps to cap the number of retries and wait longer between each one, so a struggling server is not flooded.
